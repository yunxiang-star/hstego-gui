# J-UNIWARD 提取可靠性缺陷 — 定位报告

> 发现时间：2026-09-23　发现场景：Day 6–8 评测基线（USC-SIPI 标准图库，9 张真实照片）
> 结论性质：**实测确证**，非推测。影响范围：JPEG 压缩域路径（J-UNIWARD）；空间域（S-UNIWARD）未发现同类问题。

---

## 一、一句话结论

**`hstego` 的 `extract()` 会在某些载体上确定性失败，而且完全静默**——不抛异常、不返回错误，
只往 **stdout** 打一行 `WARNING: message not found`，然后**正常写出一个 0 字节的"结果文件"**。

实测：**JPEG 压缩域 8 条里 2 条提取失败（25%）**；其中 sailboat 对任何载荷都失败，
airplane 换个载荷就失败——**失败无法从载体属性（尺寸、容量、纹理）预测**。
**`MAX_PAYLOAD = 5%` 只是安全性上限，它不保证消息能被取回。**

---

## 二、证据链（六步排除法）

### 实验 1 · 基线暴露异常

9 张图 × 双域（PNG/S-UNIWARD、JPEG/J-UNIWARD）各嵌入 128 字节**真随机**载荷：

| 域 | 执行 | 往返一致 | 失败率 |
| --- | --- | --- | --- |
| 空间域 PNG | 9 | **9 / 9** | **0%** |
| 压缩域 JPEG | 8 | **6 / 8** | **25%** ⚠️ |

失败条目：`sailboat`（容量 972B，只藏 128B）、`airplane`（容量 508B，只藏 128B）。
两者都是**做了冗余设计仍失败**——不是容量不够。

失败形态：`extract()` 耗时 **3.7–3.8 秒**（成功的要 5.7 秒）——说明它在早期就退出了。
输出文件 0 字节。

### 实验 2 · 排除"通道切分错位"假设（我最初的判断，被推翻）

初始假设：嵌入按**载体**的通道容量切分消息，提取按**载密图**的通道容量重新切分；
只要嵌入改变非零系数个数，两侧切分就错位。切分逻辑确实是严格按容量比例的：

```python
lengths[i] = (total_len * capacities[i]) // total_capacity   # hstegolib.py:384
```

**手工重现提取流程验证**（分别用两套容量各切分一次）：

```
非零系数   载体 [108467, 37914, 44715] -> 载密 [108467, 37912, 44713]   (仅漂移 -2)
有效容量   载体 [580, 172, 220]        -> 载密 [580, 172, 220]          (量化后完全不变)
[用载体容量切分]   切分=[119, 35, 45]  密文取回 199B -> 解出 OK
[用载密图容量切分] 切分=[119, 35, 45]  密文取回 199B -> 解出 OK
```

→ **切分假设排除**，载荷本体是完好的。

### 实验 3 · 定位到头部

绕过官方 `extract()`，手工走一遍：

```
头部读取失败: ValueError: MAC check failed
期望切分长度: [119, 35, 45] (和=199) -> 密文取回 199B -> 解出 OK ✅
```

**坏的是头部，不是载荷。** 32 字节头部藏在通道 0 的前 512 个位置里，
解密时 AES-EAX 的 MAC 校验不通过 → 抛异常 → 被 `extract()` 的 `try/except` 吞掉 → 静默输出空文件。

### 实验 4 · 在固定的（载体, 载荷）组合下是确定性的，不是概率抖动

同一载体重复 3 次。注意头部每次用**随机 nonce**加密（`get_random_bytes(AES.block_size)`），
所以三次的头部比特**各不相同**：

```
[rep0] 头部读取: 失败 ValueError: MAC check failed   往返 ❌ FAIL
[rep1] 头部读取: 失败 ValueError: MAC check failed   往返 ❌ FAIL
[rep2] 头部读取: 失败 ValueError: MAC check failed   往返 ❌ FAIL
```

对照组：

```
[splash]  头部读取: OK payload_len=199   往返 ✅ OK
[peppers] 头部读取: OK payload_len=199   往返 ✅ OK
```

→ **3/3 失败。与载体绑定，不是随机事件。**

### 实验 5 · 与载荷量无关

把载荷从 128B 降到 32B，同一载体仍然失败。头部是固定 32 字节，与载荷无关——**再次确认问题在头部环节**。

### 实验 6 · 换编码参数可以绕过（这是 GUI 的救命稻草）

对 sailboat 逐项换参数：

| 参数 | 容量 | 头部 | 往返 |
| --- | --- | --- | --- |
| q90 / 4:4:4（原设置） | 972 B | 坏 | ❌ FAIL |
| q90 / 4:2:0（默认子采样） | 592 B | 坏 | ❌ FAIL |
| q85 / 4:4:4 | 652 B | **OK** | ❌ **FAIL** |
| **q95 / 4:4:4** | 1820 B | OK | ✅ **OK** |
| q80 / 4:4:4 | 492 B | 坏 | ❌ FAIL |
| q90 / 载荷仅 32 B | 972 B | 坏 | ❌ FAIL |

两条重要信息：

1. **换质量确实能绕过** → GUI 的"失败后重试"策略有实测支撑。
2. **q85 那一行暴露了第二种失败模式**：头部读得出来，载荷却解不出。
   说明"头部自检"**不足以**保证整体成功——**必须做完整往返自检**。

### 实验 7 · 失败还跟载荷有关（所以不能只筛载体）

初版基线与修正版基线用了**不同的 128 字节载荷**（初版是等差序列、被 zlib 压掉，修正版是真随机）：

| 载体 | 初版载荷 | 修正版载荷（真随机） |
| --- | --- | --- |
| plane | ✅ OK | ❌ FAIL |
| sailboat | ❌ FAIL | ❌ FAIL |
| splash / baboon / peppers / barbara | ✅ OK | ✅ OK |

→ **`airplane` 换了个载荷就从成功变失败**，而 `sailboat` 怎么都失败。

**结论：失败既可能由载体触发，也可能由载荷触发，二者叠加且无法事先预测。**
这一条直接否定了"先筛一遍好载体就够了"的做法——**必须对每一次实际的（载体 + 载荷）组合做自检。**

## 三、机制分析

### 已确证的事实

| 事实 | 出处 |
| --- | --- |
| 头部 = 32 字节（`HEADER_SIZE = 16+16+8`），占通道 0 的前 **512** 个位置（`HEADER_COVER_LEN = 32×8×2`），1/2 率 STC 承载 256 比特 | `hstegolib.py:46-47, 573-577, 623` |
| 位置选择 = `random.seed(password_seed)` 后对全部系数做 `random.shuffle` | `hstegolib.py:551, 567-571` |
| **`stc_hide()` 的返回码被丢弃**：`_ = stc.stc_hide(...)` | `hstegolib.py:465` |
| 实测该返回码为 **0（自称成功）**，即使头部实际写坏 | 本报告实验 4 |
| 通道 0 非零系数仅占 **25.5% – 58.6%**，即头部那 512 个位置中 **40% – 77% 是零系数** | 9 图扫描 |
| 失败时 `extract()` 只 `print("WARNING: message not found")` 到 **stdout**，然后 `open(out,'wb').write(b"")` | `hstegolib.py:1151-1157, 333` |

### 尚未确证的部分（属 STC 引擎内部，黑箱）

以下假设被**部分证伪**，如实记录：

> 假设：J-UNIWARD 给零系数的改动代价是 INF（不可改），头部那 512 个位置里"可改位置"不足以承载 256 比特校验子。

**反例**：`splash` 前 512 位里零系数多达 **490/512（76.6%）**，只余 22 个可改位置，却**提取成功**。
而 `sailboat` 零系数 361/512（56.4%）反而失败。→ **不是简单的"wet 位置计数"问题**，
真正的判定发生在 STC 的维特比求解内部。

按课题约定，STC 当黑箱用，**不建议继续深挖**。工程上按"已知会失败 + 必须自检 + 可重试"处理即可。

## 四、对 GUI 的四条硬性要求

### 1. 嵌入后必须自检（最重要）

```
embed(cover, msg, pwd, stego)          # 官方调用
extract(stego, pwd, tmp)               # 立刻自己取一次
判定: tmp 不存在 / 为 0 字节 / sha256 != 原文  =>  视为失败
```

**不能靠 try/except**——`extract()` 不抛异常。

### 2. 失败即换参数重试

实测 q95 对失败的载体有效。建议重试序列：`q=95 → q=92 → q=88 → 换载体`。
每次重试都要重跑自检。

### 3. 容量提示必须用真实口径

`jpg_capacity()` 返回的是**密文预算**，不是"能藏多少原始字节"。
不可压缩载荷（随机数据、已压缩文件）需预留 **71 字节**开销：

```
密文长度 = 60(salt16+nonce16+tag16+magic4+len8) + len(zlib.compress(data, 9))
可藏原始字节 ≈ jpg_capacity() - 71
```

可压缩载荷（纯文本）能藏更多——zlib 会帮忙。所以 UI 必须**按用户实际上传的文件**计算，
不能只报一个容量数字，否则用户按它选文件会直接撞上 `ValueError: Message too long`。

### 4. 容量不能用尺寸估算

同为 512×512、同为 q90：`splash` 只有 **460 B**，`baboon` 有 **1532 B** —— **差 3.3 倍**。
容量高度依赖图像内容的纹理复杂度。

> ⚠️ 早前版本的容量表（"512×512 → 852 字节"）是用 `rng.normal(0, 9)` 生成的**合成噪声图**测的。
> 高斯噪声会造出海量非零 DCT 系数，数字**系统性虚高**。已作废，以真实照片基线为准。

## 五、这份发现的价值（答辩角度）

这不是一个"倒霉遇到 bug"的故事，而是**差异化第 1 条的实证**：

> 上游 GUI 只告诉你"藏好了"。
> 我们的应用会告诉你"**这个载体不适合，换一张**"或者"**已重试到 q95，藏成功且 PSNR 62 dB**"。

对应实施计划 §5.1 差异化三件事之第 1 条（"可解释的安全评估"）与第 3 条（"可复现的评测报告"）。
建议在汇报材料里作为"**失败案例分析**"（§8 第 3 项）单独呈现——比全部成功更能体现理解深度。
