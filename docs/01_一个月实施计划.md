## 一、先把这件事想清楚

### 1.1 课题是两段式的，别一上来就想做 AIGC

| 阶段 | 技术范式 | 载体从哪来 | 本阶段任务 |
| --- | --- | --- | --- |
| **阶段一（本月）** | 有载体隐写 · 最小失真框架 | 现成的图片 | 用 hstego 做一个能用的 GUI 应用 |
| **阶段二（后续）** | 无载体 / 生成式隐写 | 模型现生成 | 把秘密藏进图像生成过程本身 |

课题名里的"AIGC 生成式信息隐藏"是终点，但传统隐写是绕不过的台阶。**本月不需要碰扩散模型。**

### 1.2 最小失真框架 = 代价函数 + 隐写编码

用两句话概括 Fridrich 团队的里程碑工作：

- **代价函数（UNIWARD）**：算"改哪个像素最不容易被发现"。纹理复杂、噪声大的区域改起来便宜；平坦、平滑的区域改起来昂贵。它输出的不是"改哪里"，而是**每个像素的改造价**。
- **隐写编码（STC）**：在代价已知的前提下，找出一组修改位置，使**总代价最小，同时接收方又能正确解出消息**。

**为什么可以当黑箱**：STC 的数学门槛在于网格构造与维特比译码，但它的工程接口极其简单——`输入：每个像素的代价 + 待嵌消息 → 输出：修改位置`。做应用层完全不需要碰内部。

### 1.3 四个评价指标（demo 必须能说清楚）

1. **安全性**（最重要）：能否被隐写分析器（SRNet、Aletheia）判为含密
2. **容量**：能藏多少字节。hstego 硬性限制 ≤ **5%**
3. **不可感知性**：PSNR / SSIM，肉眼与指标双维度
4. **鲁棒性**：能否扛住微信、微博的二次压缩。hstego **不保证**，属加分项

## 三、基座工程盘点

### 3.1 hstego 由什么组成

| 模块 | 作用 | 你要懂到什么程度 |
| --- | --- | --- |
| S-UNIWARD | PNG / PGM / TIFF 等空域图像的代价函数 | 概念级即可 |
| J-UNIWARD + 代价极化 | JPEG 图像 DCT 域的代价函数 | 概念级即可 |
| STC（C++ 实现） | 最优嵌入编码 | **黑箱** |
| AES + scrypt | 消息加密、口令派生 | 会用 |
| 5% 容量上限 | 保证不被 Aletheia 可靠检测 | **必须遵守** |

读源码确认的关键事实：

- `MAX_PAYLOAD = 0.05`（hstegolib.py 第 33 行），容量上限是代码级硬约束
- 加密方案：scrypt(n=2^18, r=8) + AES，自定义头 `HS2\0` / `HC1\0`
- 空域支持格式：**png / pgm / tif**；压缩域：**jpg**
- 原生扩展通过 `ctypes.CDLL` 加载
- ⚠️ **import 时强制加载两个扩展，缺任何一个整个库直接报错**（已实测）

### 3.2 可直接调用的 API —— GUI 只需薄封装

```python
import hstegolib

# 空域（PNG）
s = hstegolib.S_UNIWARD()
s.embed("cover.png", "secret.txt", "password", "stego.png")
s.extract("stego.png", "password", "output.txt")

# 压缩域（JPEG）
j = hstegolib.J_UNIWARD()
j.embed("cover.jpg", "secret.txt", "password", "stego.jpg")
j.extract("stego.jpg", "password", "output.txt")
```

另有 `spatial_capacity(...)` / `jpg_capacity(...)` 可直接用于 UI 的**实时容量预估**。

## 五、产品定义

### 5.1 形态选型

> ⚠️ **重要发现（2026-09-20 复核源码时看到）**：hstego 仓库里**已经自带一个桌面 GUI**——
> 根目录的 `hstegogui.py`，用 Tkinter 写的向导式"隐藏 / 提取"两面板界面（含容量预估、
> 口令、进度线程）。
> **这意味着"做一个图形界面"本身不构成任何创新点**，导师随时可以点开上游仓库说"这不就是
> 官方自带的吗"。所以形态选型的真正标准不是"哪个好看"，而是**拉开与上游 GUI 的差距**。

| 方案 | 技术栈 | 优势 | 劣势 |
| --- | --- | --- | --- |
| **A. Web 应用（推荐）** | FastAPI + 单页前端 | 跨平台、易演示、方便做对比视图；手机浏览器直接打开；上游是 Tkinter，形态上天然不同 | 需要起服务 |
| B. 桌面 GUI | PySide6 / Tkinter + PyInstaller | 打包成 exe | **与上游 `hstegogui.py` 高度重合，最不推荐** |
| C. 原生 App | Kivy / Flutter | 手机体验最好 | 与 Python 基座胶水层最厚，一个月风险高 |

**建议 A 为主，前端做响应式（顺手拿到 PWA 手机端）。**

**但形态只是外壳，真正的差异化必须靠下面三件事之一**（至少做到两件）：

1. **上游只有一个算法黑箱，你给出可解释的安全评估**——检测分数、容量-安全性曲线。
   上游 GUI 只告诉你"藏好了"，你要告诉用户"藏得有多安全"。这是最大的一块空白。
2. **上游只做图像，你的架构预留 AIGC 引擎位**——为课题下一步（生成式隐写）留出接口，
   而不是一个月后推翻重写。
3. **上游是单机工具，你做可复现的评测报告**——把对照实验的原始数据、脚本、图表一起交付。

### 5.2 MVP 功能（必须完成）

1. 上传载体图 → 输入消息 / 文件 + 口令 → 生成载密图并下载
2. 上传载密图 + 口令 → 提取消息 / 文件
3. 自动路由：PNG 走 S-UNIWARD，JPG 走 J-UNIWARD
4. 实时容量预估与超限拦截（⚠️ 口径见下）
   - `jpg_capacity()` 返回的是**密文预算**，不是"能藏多少原始字节"
   - 密文长度 = `60 + len(zlib.compress(载荷, 9))` → 不可压缩载荷需预留 **71 字节**
   - **必须按用户实际上传的文件计算**，不能只报一个容量数字
5. 载体 / 载密对比视图 + 差分放大（像素差值 ×20 可视化）
6. PSNR / SSIM 实时显示
7. **嵌入后自检（新增，必做）**：embed 完成后立刻自己 extract 一次并校验 sha256；
   失败则自动换质量重试（`q95 → q92 → q88 → 换载体`），全程对用户可见
   → 这是上游 GUI 完全没有的能力，也是差异化第 1 条的直接落点

### 5.3 加分功能

8. **安全自检**：接入 RS 分析或简易 CNN 检测器，给出"被检测概率"分数——最能体现学术功底
9. 批量处理、历史记录、拖拽上传
10. 二维码 / 任意文件类型作为载荷
11. 异常场景（错误口令、超限、非图像文件）的友好提示
    ⚠️ **错误口令、提取失败、图中无消息，三者在 hstego 里症状完全相同**：都输出 0 字节文件 +
    一行 stdout WARNING。提示文案不要断言"口令错误"，应写"口令错误，或该图中没有消息，或提取失败"。
12. PWA 适配与"分享到相册"流程

### 5.4 为课题第二阶段留的接口

把隐写引擎抽象成一层接口。注意**接口的返回值必须包含"是否真的藏成功"**，
因为 hstego 的 `embed()` 返回不代表可提取（实测 JPEG 域 25% 失败）：

```python
class StegoEngine:
    def embed(cover, payload, key, **kw) -> EmbedResult   # EmbedResult.verified: bool
    def extract(stego, key) -> ExtractResult              # ExtractResult.ok / reason
```

本月实现 `HStegoEngine`，将来加 `DiffusionEngine` 时上层 UI 不用改。
**这是让项目自然长成"AIGC 生成式信息隐藏应用"的关键设计决策。**
